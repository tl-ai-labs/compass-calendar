## 1. Input Handling

The gesture handles pointer coordinates (`clientX`, `clientY`), keyboard events, and date strings generated by `dateCalcs.getDateStrByXY`.

- **Coordinate and Threshold Calculations**: Coordinate calculations in `hasExceededInteractionMoveThreshold` perform standard Euclidean distance delta checks. The calculations run in O(1) time with bounded inputs and cannot trigger infinite loops or arithmetic overflows.
- **Lexicographic Comparison in `clampDayToVisibleBounds`**:
  `clampDayToVisibleBounds(date, minDate, maxDate)` relies on string comparison (`<` and `>`) against ISO `YYYY-MM-DD` strings (`minDate` and `maxDate`):
  - **Valid ISO Dates**: Because standard `YYYY-MM-DD` dates have fixed-width, zero-padded components, lexicographical string comparison is equivalent to chronological comparison.
  - **Empty String (`""`)**: An empty string evaluates as `"" < minDate` (since length 0 is lexicographically less than any non-empty ASCII string), causing the function to safely return `minDate`.
  - **`"Invalid Date"` or Malformed Strings**: The string `"Invalid Date"` begins with ASCII character `'I'` (73), which is lexicographically greater than `'2'` (50). Thus, `"Invalid Date" > maxDate` evaluates to `true`, and the function returns `maxDate`. Any ASCII-leading string above the year `2` clamps to `maxDate`, and any string below clamps to `minDate`.
- **Range Normalization and Date Construction**: `normalizeDayRange` ensures `startDay <= endDay` via lexicographical ordering. Because inputs are clamped within `[minDate, maxDate]`, `toExclusiveAllDayEndDate` receives a valid `YYYY-MM-DD` string, and `dayjs.add(1, "day")` consistently produces a valid exclusive end date. Inverted or invalid date ranges cannot propagate into the Zustand draft store.

No input vulnerabilities, infinite loops, or crashes were found.

## 2. Global Event Listeners

During active drag gestures with visible bounds, `useAllDayDraftCreation` attaches four global listeners to `window`: `mousemove` (capture), `mouseup` (capture), `blur` (bubble), and `keydown` (capture).

- **Listener Lifecycle and Cleanup**:
  - Listeners are dynamically attached only when `visibleBounds` is provided and a primary-button `mousedown` initiates a gesture.
  - Listeners are registered alongside a cleanup routine that removes all four listeners from `window` and resets `gestureRef.current = null`.
  - Cleanup is guaranteed on gesture completion (`mouseup` via `finish`), cancellation (`Escape` or `window.blur` via `cancel`), initiation of a subsequent drag, and React component unmount (`useEffect` return cleanup).
  - Flags `isFinished` and `isCancelled` ensure teardown logic executes idempotently without dangling handlers or memory leaks.
- **Capture Phase and Event Interception**:
  - `mousemove` and `mouseup` use capture phase (`true`) to ensure pointer tracking remains uninterrupted when traversing nested DOM elements or overlay layers.
  - `mousemove` does not call `preventDefault()` or `stopPropagation()` during movement, allowing standard browser mouse tracking.
  - `mouseup` calls `preventDefault()` and `stopPropagation()` upon gesture completion to prevent accidental click propagation to underlying grid elements at the release point.
  - `keydown` capture phase handler explicitly checks for `e.key === "Escape"`:
    - When `Escape` is pressed during an active drag, `preventDefault()` and `stopPropagation()` are invoked to prevent unintended parent actions (e.g., dismissing an underlying view or modal) while cancelling the in-progress draft.
    - Non-Escape key events pass through completely unaltered.
    - Since the `keydown` listener is only attached for the brief duration of an active drag, this cannot intercept key events during normal UI navigation.

No event listener leaks, lingering capture intercepts, or use-after-unmount hazards were identified.

## 3. Denial of Service / Performance

- **Pointer Move Throttling and Thresholding**: Movement is ignored until pointer displacement exceeds `TIMED_DRAFT_CREATE_MOVE_THRESHOLD_PX` (4px), preventing redundant store updates on simple clicks or micro-jitters.
- **Update Complexity**: Each qualifying `mousemove` invokes pure, O(1) date calculations (`calculateAllDayCreateSchedule`) and updates the local Zustand draft state in memory via `draftActions.setGridDraft`.
- **Memory Retention**: Only a single active draft object is maintained in memory. No array accumulations, unthrottled recursion, heavy layout recalculations, or persistent cross-gesture references exist.

No denial of service or performance degradation risks were found.

## 4. State Integrity

- **Activity Transitions**:
  - When the gesture begins, `draftActions.startGridDraft({ activity: "creating", draft })` marks the draft store with activity `"creating"`.
  - On release (`mouseup`), `useAllDayGridDraftCreation` invokes `onCreateGridDraft`, promoting the draft to `activity: "gridClick"` and opening the draft creation form.
  - On cancellation (`Escape`, `blur`, or unmount), `draftActions.discard()` resets the draft store to `null`, clearing any partial draft state.
- **Draft Collision and Ownership**:
  - If a user presses the grid while another draft is already active (`isDrafting = true`), `useAllDayDraftCreation` immediately calls `draftActions.discard()` and returns early, avoiding conflicting or orphaned drafts.
  - In non-drag configurations (`visibleBounds` omitted, such as Day view), the interaction operates synchronously without transient `"creating"` states.

No state corruption, orphaned draft states, or unresolved activity transitions can occur.
